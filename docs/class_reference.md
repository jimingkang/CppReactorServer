# Class Reference

This document describes the main classes and structs in the current server,
client, and stress-test code. Backup/demo files under `client/*backup.cpp` and
`client/makov.cpp` are not part of the active networked game path.

## High-Level Runtime

```text
supermario_server_workers
  SocketLoop
    -> SocketMessage
    -> GateService queue
    -> ConnectionService queue
    -> SessionServiceContext(fd)
    -> Login/Hall/GameWorld/Db/Redis services
    -> SessionServiceContext(fd)
    -> SocketCommand queue
    -> SocketLoop send/close

super_mario_client
  NetworkClient
    -> parses server lines
  SuperMarioNetGame
    -> local rendering, movement, collisions
```

The service-worker server is the main Skynet-style architecture. The older
`supermario_server` and `game_server_coro` targets remain useful as simpler coroutine
reactor examples.

## Server Game Model

### `Player`

Defined in `server/supermario/super_mario_types.h`.

Represents one Super Mario/platform-game player in the server-side world.

Fields:

- `id`: stable player id assigned by `GameWorld::join`.
- `x`, `y`: latest map position reported by the client.
- `hp`: server-side hit points used by platform commands such as `ATTACK`.
- `score`: server-side score. It is updated by commands such as `MOVE`,
  `ATTACK`, and `COIN`.

### `WorldCoin`

Defined in `server/supermario/super_mario_types.h`.

Represents a Super Mario global coin generated by the server.

Fields:

- `id`: global coin id used by the client in `COIN id`.
- `x`, `y`: global map position.
- `collected`: authoritative global collected state. Once true, every client
  sees this coin as collected in subsequent `STATE` snapshots.

### `WorldMonster`

Defined in `server/supermario/super_mario_types.h`.

Represents a Super Mario global monster spawn generated by the server.

Fields:

- `id`: global monster id.
- `x`, `y`: initial map position.
- `minX`, `maxX`: patrol bounds.
- `speed`: initial horizontal speed.

The client currently simulates monster movement and collisions locally after
receiving these spawn definitions.

### `GameWorld`

Defined in `server/game_world.h`.

Abstract base interface for a complete game world.

Concrete game worlds implement:

- `join()`: allocates/attaches one player and returns the player id.
- `leave(playerId)`: removes the player and returns a protocol response.
- `handleCommand(playerId, commandLine)`: applies one text command.
- `snapshot()`: returns current text-state lines.

### `BoardGameWorld`

Defined in `server/board_game_world.h`.

Base `GameWorld` implementation point for board/card/table-style games. It
keeps board-game code separate from platform-game code while using the same
server-facing world interface.

### `PlatformGameWorld`

Defined in `server/platform_game_world.h`.

Base `GameWorld` implementation point for platform-style games. It keeps the
socket/server template independent from a specific game name.

### `supermario::SuperMarioGameWorld`

Defined in `server/supermario/super_mario_game_world.h/.cpp`.

Concrete `PlatformGameWorld` implementation for the Super Mario platform game.

Responsibilities:

- Tracks active players in `players_`.
- Tracks saved player data in `savedPlayers_` after disconnect/quit.
- Owns global coins and monster spawn configuration.
- Handles platform commands:
  - `MOVE dx dy`
  - `POS x y`
  - `ATTACK playerId`
  - `COIN coinId`
  - `STATE`

Important behavior:

- `POS` updates the player's server-side position without awarding movement
  score.
- `COIN id` marks that coin globally collected and adds 10 to the player's
  server score.
- `leave` moves the player's final `Player` data into `savedPlayers_`.
- `snapshot` emits:
  - `STATE`
  - `PLAYER`
  - `SAVED_PLAYER`
  - `COIN`
  - `MONSTER`

### `Game2048`

Defined in `server/2048/game2048.h/.cpp`.

Implements the 2048 board-game module.

Responsibilities:

- Maintains one 4x4 board per player.
- Spawns random tiles after valid moves.
- Tracks score, best score, win state, and game-over state.

Commands:

- `STATE`: returns board state.
- `MOVE LEFT|RIGHT|UP|DOWN`: applies one move.
- `RESET`: starts a new board.
- `QUIT`: exits the session.

It inherits `BoardGameWorld`, not `PlatformGameWorld`, because it is a
board-style game and does not need platform player/coin/monster state.

## Coroutine Reactor Server

### `Reactor`

Defined in `server/reactor.h/.cpp`.

Single-thread event loop based on `epoll` on Linux or `kqueue` on macOS/BSD.

Responsibilities:

- Registers fd read/write interests.
- Maps `fd -> coroutine_handle` separately for read and write waiters.
- Waits for kernel events.
- Resumes the coroutine associated with each ready fd.

Key methods:

- `readable(fd)`: returns an awaiter for read readiness.
- `writable(fd)`: returns an awaiter for write readiness.
- `run()`: blocks in `epoll_wait`/`kevent` and resumes ready coroutines.
- `stop()`: marks the loop as stopped.

### `Reactor::EventAwaiter`

Defined in `server/reactor.h/.cpp`.

Awaiter returned by `Reactor::readable` and `Reactor::writable`.

Behavior:

- `await_ready()` always returns false.
- `await_suspend(handle)` registers the current coroutine handle in `Reactor`.
- `await_resume()` is empty.

This is the bridge between `co_await reactor.readable(fd)` and the fd event
loop.

### `Task`

Defined in `server/task.h`.

Detached coroutine return type for `Server`.

Behavior:

- `initial_suspend` is `std::suspend_never`, so coroutines start immediately.
- `final_suspend` destroys the coroutine frame.
- Copying is disabled, moving is allowed.

### `Server`

Defined in `server/server.h/.cpp`.

Generic coroutine-based platform server using `Reactor`.

Responsibilities:

- Creates and owns the listening socket.
- Runs `acceptLoop`.
- Starts one `clientSession` coroutine per accepted client.
- Uses an injected `GameWorld` for command handling.

Data flow:

```text
acceptLoop
  -> clientSession(fd)
  -> recv line
  -> world_->handleCommand(playerId, line)
  -> send response
```

This class is the template for future platform-style servers:

```text
FuturePlatformServer
  -> owns Reactor-facing accept/client-session loops
  -> receives one concrete GameWorld implementation
  -> translates socket lines to world_.handleCommand(...)
  -> keeps protocol framing separate from game rules
```

For a new platform game, inherit from `PlatformGameWorld`, place the concrete
game code in its own directory, and inject it into `Server` from that game's
`main`.

### `CoroReactor`

Defined in `server/coro_reactor.h/.cpp`.

Alternative reactor implementation with clearer naming. It is functionally
similar to `Reactor`.

Key differences:

- Uses `EventKind` instead of `Interest`.
- Uses `readCoroutines_` and `writeCoroutines_` maps.
- Awaiter type is `IoAwaiter`.

### `CoroReactor::IoAwaiter`

Defined in `server/coro_reactor.h/.cpp`.

Awaiter returned by `waitReadable(fd)` and `waitWritable(fd)`.

Behavior:

- Always suspends.
- Registers the current coroutine with `CoroReactor::arm`.
- Resumes when the fd is reported ready by the reactor loop.

### `DetachedTask`

Defined in `server/coro_task.h`.

Fire-and-forget coroutine return type for `CoroGameServer`.

It mirrors `Task`: starts immediately, owns itself, and destroys the coroutine
frame at final suspend.

### `CoroGameServer`

Defined in `server/coro_server.h/.cpp`.

Alternative coroutine game server using `CoroReactor`.

Responsibilities:

- Accepts clients.
- Starts `clientLoop` per connection.
- Uses `writeAll` to asynchronously send complete responses.
- Uses the shared `GameWorld`.

## Worker / Skynet-Style Server

### `ServiceId`

Defined in `server/worker_protocol.h`.

Identifies logical services:

- `Logger`
- `Gate`
- `Connection`
- `GameWorld`
- `Room`
- `Login`
- `Db`
- `Hall`
- `Redis`

Workers are not tied to a service. They pull ready service queues from a global
queue.

### `SocketMessageType`

Defined in `server/worker_protocol.h`.

Represents socket events emitted by the socket loop:

- `Accept`
- `Data`
- `Close`
- `Error`

### `SocketMessage`

Defined in `server/worker_protocol.h`.

Message produced from fd events.

Fields:

- `type`: socket event type.
- `fd`: connection fd.
- `data`: payload for read events or error text.

### `GameCommandType` and `GameCommand`

Defined in `server/worker_protocol.h`.

Command sent from `ConnectionService` to `GameWorldService`.

Types:

- `Join`: create a game player.
- `Command`: run a client protocol command.
- `Leave`: remove/save player.

Fields:

- `fd`: connection fd to route the response.
- `playerId`: known player id for existing sessions.
- `roomId`: logical room id used by matched / joined games.
- `line`: raw protocol command for `Command`.

### `GameResponseType` and `GameResponse`

Defined in `server/worker_protocol.h`.

Response sent from `GameWorldService` back to `ConnectionService`.

Types:

- `Joined`: player id assigned and welcome text ready.
- `Text`: ordinary text response.
- `LeaveAck`: final leave response.

`closeAfterSend` tells `ConnectionService` to close the fd after the response is
written.

### `RoomMessage`

Defined in `server/worker_protocol.h`.

Used for room-side side effects emitted by `GameWorldService`.

Current use:

- `PlayerJoined`
- `PlayerLeft`

### `HallMessage`

Defined in `server/worker_protocol.h`.

Carries room-listing and matchmaking operations.

Types:

- `ListRooms`
- `CreateRoom`
- `AutoMatch`
- `CancelMatch`
- `JoinRoom`
- `LeaveRoom`
- `Result`

### `DbMessage`

Defined in `server/worker_protocol.h`.

Carries persistence and credential-check requests.

Types:

- `SavePlayer`
- `CheckCredentials`
- `CredentialsResult`

### `RedisMessage`

Defined in `server/worker_protocol.h`.

Carries the fake-Redis request/reply payload.

Types:

- `Get`
- `Set`
- `Delete`
- `KeysByPrefix`
- `Result`

### `LoginMessage`

Defined in `server/worker_protocol.h`.

Carries login request and result payloads.

Types:

- `Request`
- `Result`

### `MessageKind`

Defined in `server/worker_protocol.h`.

Discriminator for the payload stored in `SkynetMessage`.

Values:

- `Socket`
- `GameCommand`
- `GameResponse`
- `Login`
- `Log`
- `Room`
- `Db`
- `Hall`
- `Redis`

### `SkynetMessage`

Defined in `server/worker_protocol.h`.

Generic service message envelope.

Fields:

- `source`: sender service id.
- `destination`: target service id.
- `session`: reserved field.
- `requestId`: id assigned to an outbound service call.
- `replyTo`: request id that this message replies to.
- `kind`: active payload kind.
- `socket`, `gameCommand`, `gameResponse`, `login`, `room`, `db`, `hall`,
  `redis`, `text`: payload slots.

This mirrors Skynet's idea of wrapping all events as service messages.

### `ServiceContext`

Defined in `server/service_context.h/.cpp`.

Per-service mailbox.

Responsibilities:

- Holds `SkynetMessage` objects for one service.
- Tracks whether the queue is already scheduled in the global ready queue.
- Lets a worker pop messages one by one.
- Lets the worker mark a batch finished and decide whether to reschedule.

Important methods:

- `push(message)`: adds a message and returns true if the queue should be
  scheduled.
- `popOne(message)`: pops one message.
- `finishBatch()`: clears scheduled state if empty, otherwise asks for
  rescheduling.

This queue object is the stable base of the current "queue + coroutine"
dispatcher.

### `CoroutineServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Base class for services that process mailbox messages in a long-lived
coroutine.

Responsibilities:

- Starts `mainLoop()` lazily on first dispatch.
- Buffers inbound messages in `inbox_`.
- Resumes the service coroutine until it blocks on `nextMessage()`.

Current users:

- `LoggerServiceContext`
- `RoomServiceContext`
- `DbServiceContext`
- `RedisServiceContext`

### `RequestReplyServiceContext`

Defined in `server/request_reply_service_context.h/.cpp`.

Base class for services that need mailbox processing plus nested
service-to-service request/reply.

Responsibilities:

- Supports `nextMessage()` mailbox suspension.
- Supports `callService(request)` suspension.
- Tracks pending calls by `requestId`.
- Resumes the suspended coroutine when a reply arrives with matching `replyTo`.

### `SocketCommandType` and `SocketCommand`

Defined in `server/worker_protocol.h`.

Command sent from services back to the socket loop.

Types:

- `Send`: append text to a fd output buffer.
- `Close`: close after queued output is flushed.

Workers never call `send` or `close` directly.

### `WorkerGameServer`

Defined in `server/worker_server.h/.cpp`.

Main Skynet-style server implementation.

Responsibilities:

- Owns the listening socket and all connection fds.
- Runs the socket event loop.
- Owns all service contexts.
- Owns the global queue of ready service queues.
- Starts and stops worker threads.
- Starts a fixed-step world tick thread.
- Converts fd events into `SocketMessage`.
- Converts service responses into `SocketCommand`.

Important private structs:

- `ClientSocket`: socket-loop state, including output buffer and close flag.

Important methods:

- `handleGateService`: forwards socket events to connection service.
- `handleConnectionService`: creates and routes `SessionServiceContext`
  instances by fd.
- `handleGameWorldService`: calls `GameWorld` and emits room/db/connection side
  effects.
- `sendToContext`: pushes a message into one service mailbox and schedules it.
- `rescheduleService`: requeues a service when a worker batch drained only part
  of the mailbox.
- `drainSocketCommands`: flushes worker-generated `Send` and `Close` commands
  back into socket-loop-owned fd state.

Service inventory:

- `LoggerServiceContext`
- `GateServiceContext`
- `ConnectionServiceContext`
- `GameWorldServiceContext`
- `RoomServiceContext`
- `LoginServiceContext`
- `DbServiceContext`
- `HallServiceContext`
- `RedisServiceContext`

Data flow:

```text
socketLoop
  -> queueSocketMessage(SocketMessage)
  -> Gate queue
  -> Connection queue
  -> SessionServiceContext(fd)
  -> Login/Hall/GameWorld/Db/Redis queues
  -> SessionServiceContext(fd)
  -> queueSocketCommand(Send/Close)
  -> socketLoop flush
```

### `SessionServiceContext`

Defined in `server/session_service_context.h/.cpp`.

Per-connection coroutine service wrapper around one `ISessionAgent`.

Responsibilities:

- Receives socket events for one fd.
- Receives login/hall/world replies for that same fd.
- Applies `SessionActions` returned by the session agent.
- Converts one selected service message at a time into a blocking
  `callService(...)`.
- Retires and clears the session when the agent asks to erase it.

The blocking service calls extracted by `processSessionActions()` are:

- login request
- hall request
- world `Join`
- world `Leave`
- world `QUIT`

### `GateServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Thin queue endpoint that forwards socket events from the socket loop into
`ConnectionService`.

### `ConnectionServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Thin queue endpoint that routes messages to per-fd `SessionServiceContext`
instances.

It handles:

- accept -> create session context
- data -> forward to session
- close/error -> forward to session or close directly if no session exists
- login/hall/game responses -> route reply back to owning session

### `GameWorldServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

`RequestReplyServiceContext` wrapper around
`WorkerGameServer::handleGameWorldService()`.

### `LoggerServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Coroutine mailbox service that prints `MessageKind::Log` payloads to stdout.

### `LoginServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Coroutine request/reply service for authentication.

Flow:

```text
Login request
  -> Db CheckCredentials
  -> Db CredentialsResult
  -> Login Result
  -> Connection / Session
```

### `DbServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Coroutine mailbox service that currently provides:

- in-memory credential lookup seeded from `IGameServerBinding::seedUsers()`
- `SavePlayer` logging hook

### `HallServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Coroutine request/reply service for room listing, room lifecycle, and
auto-match.

Responsibilities:

- Owns `rooms_`
- Owns auto-match queues keyed by `(gameType, seatCount)`
- Allocates room ids
- Writes hall state mirrors into `RedisServiceContext`
- Replies directly to waiting sessions with `HallMessageType::Result`

### `RedisServiceContext`

Defined in `server/service_runtime_contexts.h/.cpp`.

Coroutine mailbox service implementing an in-process key/value store with a
Redis-like request shape.

## Client

### `Vec2`

Defined in `client/super_mario_client.cpp`.

Simple float vector used for positions and velocities.

### `Platform`

Defined in `client/super_mario_client.cpp`.

Local render/collision platform rectangle.

Fields:

- `x`, `y`, `w`, `h`

### `RemotePlayer`

Defined in `client/super_mario_client.cpp`.

Parsed representation of a server `PLAYER` line.

Fields:

- `id`
- `x`, `y`
- `hp`
- `score`

### `Coin`

Defined in `client/super_mario_client.cpp`.

Client representation of a server-generated global coin.

Fields:

- `id`: server coin id.
- `x`, `y`: map position.
- `collected`: true if the server or local collision marked it collected.

When the local player touches a coin, the client sends `COIN id` to the server.

### `Monster`

Defined in `client/super_mario_client.cpp`.

Client representation of a server-generated monster spawn.

Fields:

- `id`
- `x`, `y`
- `minX`, `maxX`
- `speed`
- `alive`

Monster movement and collision are currently simulated client-side after the
server provides the spawn data.

### `NetworkClient`

Defined in `client/super_mario_client.cpp`.

Non-blocking TCP client for the text protocol.

Responsibilities:

- Connects/disconnects.
- Sends newline-terminated commands.
- Polls socket reads.
- Splits received data into lines.
- Parses:
  - `WELCOME`
  - `PLAYER`
  - `COIN`
  - `MONSTER`
- Stores recent server log lines.
- Stores remote players and world-object definitions.

Important methods:

- `connectTo(host, port)`: opens a TCP connection and sends initial `HELP` and
  `STATE`.
- `disconnect()`: closes socket and clears local network state.
- `sendLine(line)`: queues a protocol command.
- `poll()`: flushes writes and consumes all available input.

### `IGameClientView`

Defined in `client/super_mario_client.cpp`.

Client-side view interface for a playable screen.

Methods:

- `update(window, dt, network)`
- `draw(drawList, origin, size, network)`

New client games should implement this interface instead of modifying socket
code.

### `SuperMarioNetGame`

Defined in `client/super_mario_client.cpp`.

Main client-side Super Mario game view.

Responsibilities:

- Handles local movement and gravity.
- Sends `POS x y` periodically.
- Requests `STATE` periodically.
- Draws sky, scenery, platforms, coins, monsters, remote players, Mario, and
  HUD.
- Syncs server-generated coins and monsters from `NetworkClient`.
- Performs local collision detection:
  - platform landing
  - coin collection
  - monster stomp
  - monster side hit
- Sends `COIN id` when the player collects a coin.
- Sends `QUIT` and disconnects when local score reaches 0.

Important state:

- `position_`, `velocity_`: local player physics.
- `hp_`: currently displayed HP.
- `localScore_`: local score used by client-side monster/coin rules.
- `coins_`: local copy of server-generated global coins.
- `serverMonsters_`: original server monster spawns.
- `monsters_`: live client-side monster simulation.

## Stress Client

### `Config`

Defined in `client/stress_client.cpp`.

Runtime settings for the pressure client:

- host
- port
- total request count
- concurrency
- command
- expected response prefix

Defaults target `127.0.0.1:7779`, one million `PING` requests, and a concurrency
based on hardware threads.

### `WorkerStats`

Defined in `client/stress_client.cpp`.

Per-stress-worker metrics:

- success count
- failure count
- sampled latency values in microseconds

The stress client aggregates these into total success/failure, QPS, average
latency, and p50/p95/p99.

## Build / Test Notes

Current build targets relevant to the worker architecture include:

- `supermario_server_workers`
- `guess_number_server_workers`
- `guess_number_client`
- `game2048_client`
- `stress_client`

Typical local build commands:

```bash
cmake -S . -B build -DBUILD_IMGUI_CLIENT=ON
cmake --build build --target guess_number_server_workers
cmake --build build --target guess_number_client
```

Typical startup smoke test for guess-number:

```bash
./build/guess_number_server_workers 127.0.0.1 7799 1
```

The current repository state does not expose automated `ctest` coverage for
this path:

```bash
ctest --test-dir build -N
```

Expected result:

```text
Total Tests: 0
```

So "test" currently means build verification plus manual startup / connection
smoke testing.

## Protocol Summary

Client-to-server commands:

```text
HELP
PING
QUIT
STATE
POS x y
MOVE dx dy
ATTACK playerId
COIN coinId
BOARD
PLAY cell
RESET_BOARD
```

Server-to-client lines:

```text
WELCOME player=N type HELP
PONG
OK ...
ERR ...
BYE player=N
STATE players=N
PLAYER id=N x=X y=Y hp=H score=S
SAVED_PLAYER id=N x=X y=Y hp=H score=S
COIN id=N x=X y=Y collected=0|1
MONSTER id=N x=X y=Y min=A max=B speed=S
```

## Extension Guide

Adding a new server game:

```text
1. Inherit from GameWorld for a complete standalone game.
2. Inherit from BoardGameWorld for board/card/table-style games.
3. Store game state inside that class.
4. Emit protocol lines from snapshot/handleCommand.
5. Add a dedicated server target if the game should run independently.
6. For platform-style socket servers, use Server as the server-loop template.
```

Adding a new client game:

```text
1. Implement IGameClientView.
2. Parse needed server lines in NetworkClient or a game-specific parser.
3. Draw the view and send protocol commands through NetworkClient::sendLine.
```

Adding a new worker service:

```text
1. Add a ServiceId value.
2. Add a payload/message type in worker_protocol if needed.
3. Choose a base:
   - ServiceContext
   - CoroutineServiceContext
   - RequestReplyServiceContext
4. Register the service context in WorkerGameServer.
5. Route callers to that service with sendToService / callService.
```
